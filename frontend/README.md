# Foundation frontend mapping

This mapping is based on `backend/src/app.ts`, the identity/organisation/team services and repositories, `backend/src/shared/auth/authorization.ts`, and `backend/src/config/env.ts`. The UI calls the existing API through a same-origin Next.js proxy and does not duplicate backend authorization or business rules.

The signed-in workspace provides role-aware Capstone support pages against existing APIs: support dashboard, ticket intake with product/affected-service fields and optional attachment upload, searchable/filterable/sortable paginated queue, ticket detail and audit history, AI analysis/triage, similar-ticket/knowledge results, editable resolution drafts, support-lead escalation and AI approval queues, operational reports, ticket audit, and a view of existing configuration. The backend remains authoritative for ticket scope and each operation. AI output does not automatically change ticket status, priority or team assignment. On configured resolved transitions, the resolution workspace records the human-edited resolution note, outcome and customer-confirmation evidence through the existing status API. It does not save standalone ratings of AI resolution quality; triage approval records a decision and comment.

After `/api/v1/me` resolves the active organisation, support-only memberships (`support_agent`, `support_lead`, or `requester`) land in **Support → Support tickets** and do not see the administration navigation. Organisation administrators land in **Administration → Overview** and also have the support workspace when ticket permissions are present. Switching organisations recalculates the landing page from that membership's permissions.

For support leads, the support page presents **Team & unassigned**, **Escalations**, and **AI approvals** tabs. Escalations are team-scoped records with required reason and handover notes; P1 priority changes open one automatically, while staff may explicitly escalate P2, SLA-risk, recurring-breach, or beyond-authority cases. Leads record follow-up before closing an escalation. The SLA threshold candidate is still draft, so this implementation does not auto-escalate on time percentages or send outbound notifications. The AI review queue offers accepted, rejected, or needs-information decisions with required reviewer comments; stale or redacted reports are excluded. Requesters and agents receive only server-scoped tickets and controls allowed by their permissions; administrators retain their Foundation pages and receive support pages only when their effective permissions allow them.

Dashboard queue counts and team workload are calculated from tickets visible to the signed-in role. SLA risk and period reports use the backend report API and therefore appear only for roles granted report access. Audit is assembled from ticket-scoped histories (and triage review decisions where permitted), not a global audit feed. Configuration shows teams, routing rules, and administrator-only workflows. Organisation administrators can upload TXT, Markdown, PDF, or DOCX policy sources, extract candidate rules, review candidates with a reason, and explicitly publish approved evidence for AI retrieval. They can also create a structured SLA policy version tied to a document version, then approve and activate it as separate actions. The upload itself never activates SLA targets; the backend validates the payload and remains authoritative. Published evidence supports authorised similarity and resolution retrieval; it does not alter the priority matrix. Categories/priority CRUD are not offered because no tenant APIs define them.

| Backend functionality | Existing API endpoint | Frontend page/component | Supported actions |
|---|---|---|---|
| Current authenticated identity, active organisations, roles and derived permissions | `GET /api/v1/me`; `GET /api/v1/me?organisationId={id}` | Connection panel, organisation selector, account menu | Inspect current identity and active membership context; choose a returned organisation. |
| User's active organisations | `GET /api/v1/organisations` | Organisation overview and selector | List the caller's active organisations. |
| Organisation detail and update | `GET /api/v1/organisations/{id}`; `PATCH /api/v1/organisations/{id}` | Organisation settings page | View details; update name, settings object, or status (`active`, `inactive`, `suspended`) when permitted. |
| Create organisation and grant creator administrator membership | `POST /api/v1/organisations` with `{name}` | Organisations page | Create an organisation under backend permission and uniqueness checks. |
| Tenant users and membership roles/permissions | `GET /api/v1/users`; `GET /api/v1/users/{id}` | Users page and user detail drawer | List active users with active memberships; inspect an active user's roles and derived permissions. |
| Invite/provision user and active organisation membership | `POST /api/v1/users` with `{email, displayName, roles}` | Invite user dialog | Invite when backend Keycloak provisioning is configured. API may return `IDENTITY_PROVISIONING_UNAVAILABLE`; the UI reports this without pretending the invite succeeded. |
| Change organisation membership state and roles | `PUT /api/v1/users/{id}/memberships` with `{status, roles}` | User detail drawer | Set status (`active`, `inactive`, `suspended`) and one or more supported roles. Backend controls authorization and account activation requirements. |
| Update user display name | `PATCH /api/v1/users/{id}` with `{displayName}` | User detail drawer | Update display name only; backend Keycloak provisioning must be configured. Email and account status are not editable through this operation. |
| Role capability descriptions | `GET /api/v1/roles` | Role selector and permission preview | Display the four backend role templates and their permission descriptions. Requires `users.manage`. |
| Departments | `GET /api/v1/departments`; `POST /api/v1/departments` with `{name}` | Teams page | List and create departments. No update/delete route exists. |
| Teams and department association | `GET /api/v1/teams`; `POST /api/v1/teams` with `{name, departmentId?}`; `PATCH /api/v1/teams/{id}` with permitted fields | Teams page and team detail drawer | List, create, rename, and associate/remove a department. Department IDs are tenant-validated by the backend. No delete route exists. |
| Team memberships | `GET /api/v1/teams/{id}/members`; `PUT /api/v1/teams/{id}/members` with `{userId, role, status}` | Team detail drawer | List active memberships; set a member's role (`support_lead`, `support_agent`, `requester`) and status (`active`, `inactive`, `suspended`). The user must already be active in the organisation. |
| Requester ticket intake | `POST /api/v1/tickets` with `{title, description, product?, affectedService?, affectedUsers, businessImpact, urgency}`; `POST /api/v1/tickets/{id}/attachments` | Support tickets page, create-ticket form | Submit title/description, optional product/service, affected-user scope/count, business impact and urgency; attachments upload separately. Requester and organisation are derived from authenticated backend identity/membership, and timestamps are assigned by the backend. |

## Backend constraints reflected in the UI

- Protected routes require a Keycloak bearer access token and, for tenant routes, the `X-Organisation-ID` header. `/api/v1/me` without a selected organisation returns only active memberships in active organisations.
- Roles and permissions are server-derived. The client uses returned permissions to guide visibility, while every API operation remains protected by backend authorization.
- Lists use `page` and `pageSize` query parameters (default page size 20, maximum 100) and return `{data, pagination, requestId}`.
- Errors use `{error: {code, message, requestId, fields?}}`; the UI preserves field-level messages and request IDs where available.
- No user delete, organisation delete, department update/delete, or team delete API exists, so the UI does not offer those actions.
- Sign-in uses the existing Keycloak `support-web` public client and authorization-code flow with PKCE S256. The browser adapter keeps tokens in memory and refreshes them before API requests; no access token is saved in web storage. The API's `/api/v1/me` response supplies active organisation memberships and server-derived permissions used for role-aware navigation and actions.
- Configure `NEXT_PUBLIC_KEYCLOAK_URL`, `NEXT_PUBLIC_KEYCLOAK_REALM`, `NEXT_PUBLIC_KEYCLOAK_CLIENT_ID`, and `BACKEND_API_URL` in `frontend/.env.local` (copy `.env.example`). Add the frontend origin and redirect URI to the Keycloak client's allowed values. Updating `deploy/keycloak/realm/ai-support-realm.json` affects new realm imports only; update an already-created local realm in the Keycloak Admin Console.
- The offline demo token is not a Keycloak token and cannot authenticate to the normal backend configuration.
